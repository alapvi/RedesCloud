    AWS · Security Groups y Network ACL¶

    Routing decide si existe camino. Security Groups y NACL deciden qué tráfico puede utilizar ese camino.

    1. Política objetivo¶

    Internet → WEB:443
WEB      → APP:8080
APP      → DB:5432

    Las demás nuevas conexiones no necesarias deben permanecer bloqueadas.

    2. Dos mecanismos distintos¶

    Característica Security Group Network ACL
    nivel recurso / ENI subnet
    estado stateful stateless
    ALLOW sí sí
    DENY explícito no sí
    orden de reglas no sí
    referencia a SG sí no
    uso principal política por recurso/rol barrera adicional de subnet

    No deben enseñarse como dos firewalls equivalentes.

    3. Security Groups¶

    Asociamos:

    EC2-WEB → SG-WEB
EC2-APP → SG-APP
EC2-DB  → SG-DB

    SG-WEB¶

    Inbound
TCP/443
Source: 0.0.0.0/0

    Para administración, evitar SSH abierto a Internet si no es necesario.

    SG-APP¶

    Inbound
TCP/8080
Source: SG-WEB

    SG-DB¶

    Inbound
TCP/5432
Source: SG-APP

    4. Referencias entre SG¶

    En lugar de decir:

    Source: 10.0.10.0/24

    podemos expresar:

    Source: SG-WEB

    La política se asocia al rol del recurso y no a una IP concreta.

    Esto mantiene la lógica incluso si cambia la dirección privada de una instancia.

    5. Stateful¶

    Si SG-APP permite:

    WEB → APP:8080

    el tráfico de respuesta asociado puede volver automáticamente.

    No necesitamos una regla inversa para esa respuesta.

    Sin embargo, una nueva conexión:

    APP → WEB

    sí requeriría autorización propia.

    6. Outbound¶

    Los SG también controlan salida.

    Para la primera práctica podemos mantener egress permisivo y centrarnos en inbound. Como ampliación podemos restringir salida para estudiar egress filtering y exfiltración.

    7. Network ACL¶

    Una NACL se aplica a una subnet.

    SUBNET-WEB → NACL
SUBNET-APP → NACL
SUBNET-DB  → NACL

    Su característica esencial es que es stateless.

    8. Stateless y puertos efímeros¶

    Supongamos:

    WEB:49152 → APP:8080

    La respuesta será:

    APP:8080 → WEB:49152

    La NACL debe permitir ambos sentidos.

    Una configuración que solo contemple TCP/8080 puede bloquear el retorno por el puerto efímero del cliente.

    9. ALLOW y DENY¶

    Las NACL admiten ambas acciones y evalúan reglas por número, de menor a mayor.

    100 DENY  10.0.10.0/24
110 ALLOW 10.0.10.0/24 TCP 8080

    La regla 100 coincide primero y bloquea.

    El orden forma parte de la política.

    10. Papel de cada mecanismo¶

    Nuestra estrategia será:

    Security Groups
→ política principal WEB→APP→DB

NACL
→ segunda capa / control grueso de subnet

    Esto mantiene la arquitectura comprensible y evita duplicar innecesariamente la misma lógica en dos sitios.

    11. Camino conceptual¶

    EC2 origen
 ↓
SG outbound
 ↓
NACL subnet origen
 ↓
Route Table
 ↓
NACL subnet destino
 ↓
SG inbound
 ↓
EC2 destino
 ↓
servicio

    Cada etapa puede romper una comunicación.

    12. Validación WEB → APP¶

    En APP:

    python3 -m http.server 8080

    Desde WEB:

    curl http://IP_PRIVADA_APP:8080

    Esperado: ✓

    13. Validación WEB → DB¶

    Desde WEB:

    nc -vz IP_PRIVADA_DB 5432

    Esperado: ✕

    La ruta local existe, pero SG-DB no permite origen SG-WEB.

    14. Validación APP → DB¶

    En DB podemos levantar temporalmente un listener TCP de prueba sobre 5432.

    Desde APP:

    nc -vz IP_PRIVADA_DB 5432

    Esperado: ✓

    El objetivo es comprobar conectividad TCP, no simular una base PostgreSQL real.

    15. Matriz de pruebas¶

    Flujo Esperado
    Internet→WEB:443 ✓
    Internet→APP:8080 ✕
    Internet→DB:5432 ✕
    WEB→APP:8080 ✓
    WEB→DB:5432 ✕
    APP→DB:5432 ✓
    DB→APP nueva ✕

    16. Fallo: origen incorrecto en SG¶

    Configura SG-APP con un origen que no corresponda a SG-WEB.

    La ruta seguirá existiendo, pero TCP/8080 fallará.

    Esto permite distinguir reachability de authorization.

    17. Fallo: puerto incorrecto¶

    Configura 8081 mientras el servicio escucha en 8080.

    routing ✓
servicio ✓
policy ✕

    18. Fallo: NACL bloqueando retorno¶

    Permite la ida hacia 8080 pero bloquea los puertos efímeros de retorno.

    La conexión no se completa aunque el Security Group sea correcto.

    Este escenario demuestra con claridad:

    SG → stateful
NACL → stateless

    19. Troubleshooting SG¶

    1. SG asociado al recurso
2. inbound correcto
3. source correcto
4. protocolo
5. puerto
6. outbound suficiente

    20. Troubleshooting NACL¶

    1. NACL de subnet origen
2. outbound origen
3. NACL subnet destino
4. inbound destino
5. retorno
6. puertos efímeros
7. orden de reglas

    21. Seguridad distribuida¶

    OPNsense representaba un firewall central explícito.

    En AWS:

    WEB [SG-WEB]
   ↓
APP [SG-APP]
   ↓
DB [SG-DB]

    la política se distribuye junto a los recursos.

    Este cambio de modelo es una de las ideas más importantes del bloque cloud.

    22. Movimiento lateral¶

    Si WEB queda comprometido:

    WEB comprometido
  ├── APP:8080 ✓
  └── DB:5432 ✕

    La política limita el alcance del compromiso.

    Modelo mental¶

    Route Table
→ reachability

Security Group
→ política stateful por recurso

NACL
→ política stateless por subnet

    Security Groups expresan mejor quién puede hablar con quién. NACL añade una frontera adicional de subnet.
