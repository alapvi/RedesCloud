    UD2 · Troubleshooting de redes on-premise y AWS¶

    Objetivo: desarrollar un método sistemático para localizar fallos de conectividad en arquitecturas Proxmox/OPNsense y AWS, utilizando el packet path, evidencias técnicas y aislamiento progresivo de la causa.

    1. Troubleshooting no es probar cosas al azar¶

    Ante un problema de red, una estrategia incorrecta sería:

    cambiar firewall
↓
cambiar rutas
↓
reiniciar
↓
cambiar DNS
↓
abrir any-any
↓
volver a probar

    Aunque finalmente funcione, no habremos demostrado:

    qué fallaba
por qué fallaba
qué cambio lo corrigió

    Nuestro método será:

    SÍNTOMA
   ↓
ALCANCE
   ↓
PACKET PATH
   ↓
HIPÓTESIS
   ↓
EVIDENCIA
   ↓
CAUSA RAÍZ
   ↓
CORRECCIÓN MÍNIMA
   ↓
VALIDACIÓN

    2. Primera pregunta: ¿qué debería ocurrir?¶

    Antes de diagnosticar debemos definir el comportamiento esperado.

    No es suficiente:

    “No funciona APP.”

    Debemos concretar:

    WEB
10.10.10.10
   │
   │ TCP/8080
   ▼
APP
10.10.20.10

    Esperado:

    ALLOW

    Mientras:

    WEB
   │
   │ TCP/5432
   ▼
DB

    Esperado:

    DENY

    Un fallo puede ser:

    algo permitido no funciona

    pero también:

    algo prohibido funciona

    3. Determinar el alcance¶

    Preguntamos:

    ¿falla un host?
¿falla una VLAN?
¿falla una subnet?
¿falla un protocolo?
¿falla un puerto?
¿falla Internet?
¿falla solo DNS?
¿falla todo AWS?

    Ejemplos:

    Síntoma Alcance inicial
    WEB no alcanza APP:8080 flujo concreto
    ninguna VM de VLAN20 comunica VLAN/subnet
    APP llega a IP externa pero no a nombres DNS
    APP y DB pierden Internet routing/NAT compartido
    solo EC2-APP falla recurso/SG/subnet

    Cuanto mejor definamos el alcance:

    menos componentes tendremos que investigar

    4. Reconstruir el packet path¶

    La pregunta fundamental será siempre:

    ¿Qué camino debería recorrer el paquete?

    5. Packet path on-premise¶

    Ejemplo:

    WEB
10.10.10.10
   │
   │ VLAN10
   ▼
vmbr1
   │
   ▼
OPNsense
10.10.10.1
   │
   │ routing + firewall
   ▼
OPNsense
10.10.20.1
   │
   │ VLAN20
   ▼
vmbr1
   │
   ▼
APP
10.10.20.10

    Debemos poder detenernos en cada punto y preguntar:

    ¿el paquete debería llegar hasta aquí?

    6. Packet path AWS¶

    Ejemplo WEB → APP:

    EC2-WEB
   ↓
Security Group
   ↓
NACL
   ↓
VPC routing
   ↓
NACL
   ↓
Security Group
   ↓
EC2-APP
   ↓
servicio TCP/8080

    Este esquema es un modelo mental de diagnóstico, no una representación física del interior de AWS.

    7. Diagnóstico por capas¶

    Utilizaremos esta secuencia:

    CAPA 1
estado / enlace
    ↓
CAPA 2
bridge / VLAN / MAC
    ↓
CAPA 3
IP / máscara / gateway / routing
    ↓
CAPA 4
TCP / UDP / puertos
    ↓
SEGURIDAD
firewall / SG / NACL
    ↓
NAT
    ↓
DNS
    ↓
APLICACIÓN

    No siempre necesitaremos recorrerlas todas.

    8. Regla fundamental¶

    Comenzamos en el punto más próximo al origen en el que podamos demostrar algo.

    Y avanzamos progresivamente hacia el destino.

    9. Nivel 1 · Estado de la interfaz¶

    En Linux:

    ip -br link

    Comprobar:

    UP

    Después:

    ip -br addr

    Preguntas:

    ¿existe la interfaz?
¿está UP?
¿tiene la IP esperada?

    10. Nivel 2 · VLAN y switching¶

    En Proxmox:

    bridge link
bridge vlan show
bridge fdb show br vmbr1

    Preguntas:

    ¿VM conectada al bridge correcto?
¿VLAN Tag correcto?
¿vmbr1 es VLAN-aware?
¿VLAN permitida?
¿se aprende la MAC?

    11. ARP¶

    En una VM:

    ip neigh

    Podemos limpiar temporalmente:

    sudo ip neigh flush all

    y generar tráfico.

    Captura:

    tcpdump -eni <interfaz> arp

    12. Interpretar neighbor table¶

    Ejemplo:

    10.10.10.1 FAILED

    puede indicar:

    gateway inexistente
VLAN incorrecta
bridge incorrecto
interfaz caída
problema L2

    No deberíamos investigar todavía:

    DNS
NAT
aplicación

    13. Pregunta ARP fundamental¶

    Si WEB:

    10.10.10.10/24

    quiere alcanzar:

    10.10.20.10

    debe hacer ARP para:

    10.10.10.1

    No para:

    10.10.20.10

    Si intenta resolver directamente 10.10.20.10, debemos revisar:

    máscara
routing local

    14. Nivel 3 · Routing del host¶

    Comprobar:

    ip route

    y después:

    ip route get DESTINO

    Ejemplo:

    ip route get 10.10.20.10

    Esperamos:

    via 10.10.10.1

    15. ip route get es especialmente útil¶

    Porque responde:

    ¿Qué haría realmente este host con este destino?

    No solo:

    “¿Qué rutas tengo configuradas?”

    16. Gateway¶

    Probar:

    ping -c 3 10.10.10.1

    Si no alcanzamos el gateway:

    NO tiene sentido empezar por NAT
NO tiene sentido empezar por DNS
NO tiene sentido empezar por Internet

    17. Routing inter-VLAN¶

    Si:

    gateway ✓

    pero:

    WEB → APP ✕

    investigamos:

    routing OPNsense
firewall
retorno

    18. Camino de retorno¶

    Nunca debemos estudiar únicamente:

    A → B

    También:

    B → A

    Una petición puede llegar al destino pero la respuesta no regresar.

    Ejemplo:

    WEB
→ APP
✓

APP
→ WEB
sin gateway
✕

    Resultado para el usuario:

    “no funciona”

    aunque el paquete inicial haya llegado.

    19. Nivel 4 · Servicio¶

    Antes de culpar a la red:

    ss -lntp

    Ejemplo:

    APP debería escuchar TCP/8080

    Comprobar:

    ss -lntp | grep 8080

    20. Probar el protocolo correcto¶

    Para HTTP:

    curl -v http://10.10.20.10:8080

    Para TCP:

    nc -vz 10.10.20.10 8080

    21. Ping no es suficiente¶

    ping ✕

    no implica necesariamente:

    servidor caído

    Puede existir:

    ICMP bloqueado
+
TCP/8080 permitido

    Por tanto:

    La prueba debe representar el servicio real que queremos validar.

    22. Firewall OPNsense¶

    Si:

    routing ✓
servicio ✓

    pero la conexión falla:

    revisar:

    interfaz de entrada
source
destination
protocol
destination port
rule order
state

    23. ¿En qué interfaz?¶

    Para:

    WEB → APP

    el paquete entra en OPNsense por:

    WEB

    Por tanto la política se analiza desde esa interfaz.

    24. Firewall Log¶

    El log permite responder:

    ¿llegó el paquete?
¿qué interfaz lo recibió?
¿qué decisión tomó el firewall?

    Si observamos:

    BLOCK
10.10.10.10
→
10.10.20.10:8080

    tenemos una evidencia muy fuerte.

    25. State table¶

    OPNsense es stateful.

    Una conexión ya establecida puede seguir teniendo estado después de modificar reglas.

    Por ello:

    cambiar regla
↓
probar

    puede producir conclusiones incorrectas.

    Cuando corresponda:

    revisar state
↓
eliminar state
↓
repetir prueba

    26. Packet capture¶

    Utilizar:

    tcpdump

    o Packet Capture de OPNsense.

    Preguntas:

    ¿entra el paquete?
¿sale?
¿aparece la respuesta?
¿en qué interfaz desaparece?

    27. Estrategia de dos capturas¶

    Ejemplo WEB → APP:

    CAPTURA 1
interfaz WEB

    y:

    CAPTURA 2
interfaz APP

    Interpretación:

    entra por WEB ✓
sale por APP ✕

    El problema se encuentra:

    en OPNsense

    o en su decisión de routing/política.

    28. NAT¶

    Para salida a Internet:

    APP
→ OPNsense
→ WAN
→ Internet

    debemos diferenciar:

    routing
firewall
NAT
DNS

    29. Diagnóstico de Internet¶

    Seguir:

    1. gateway
2. IP externa
3. DNS
4. aplicación

    Ejemplo:

    ping 10.10.20.1

    después:

    ping 1.1.1.1

    después:

    getent hosts example.com

    después:

    curl -I https://example.com

    30. Interpretación rápida¶

    Gateway IP externa DNS Hipótesis
    ✕ ✕ ✕ L2/L3/gateway
    ✓ ✕ ✕ firewall/NAT/WAN/routing
    ✓ ✓ ✕ DNS
    ✓ ✓ ✓ revisar aplicación/protocolo

    31. Comprobar NAT mediante captura¶

    Captura interna:

    src = 10.10.20.10

    Captura WAN:

    src = IP_WAN_OPNsense

    Si podemos demostrar ambas:

    SNAT ✓

    32. DNS¶

    Si:

    1.1.1.1 ✓

    pero:

    example.com ✕

    no debemos modificar:

    VLAN
routing
NAT

    sin evidencia adicional.

    Investigamos:

    DNS

    33. Árbol rápido on-premise¶

    ¿Interfaz UP?
   │
   ├── NO → interfaz / VM
   │
   └── SÍ
        ↓
¿IP/máscara correctas?
   │
   ├── NO → configuración L3
   │
   └── SÍ
        ↓
¿VLAN/bridge correctos?
   │
   ├── NO → Proxmox / 802.1Q
   │
   └── SÍ
        ↓
¿Gateway alcanzable?
   │
   ├── NO → ARP / VLAN / gateway
   │
   └── SÍ
        ↓
¿Ruta correcta?
   │
   ├── NO → routing
   │
   └── SÍ
        ↓
¿Firewall permite?
   │
   ├── NO → reglas / state
   │
   └── SÍ
        ↓
¿Servicio escucha?
   │
   ├── NO → aplicación
   │
   └── SÍ
        ↓
¿Internet?
   │
   ├── NO → NAT/WAN
   │
   └── SÍ
        ↓
¿Nombre DNS?
   │
   ├── NO → DNS
   │
   └── SÍ → cadena funcional

    34. Troubleshooting en AWS¶

    En AWS cambia la implementación.

    No cambia la metodología.

    Seguimos preguntando:

    ¿qué camino debería recorrer el paquete?

    35. Empezar por el recurso¶

    Comprobar:

    EC2 state
private IPv4
subnet
Security Groups asociados

    Preguntas:

    ¿es la instancia correcta?
¿está en la subnet correcta?
¿estamos utilizando la IP correcta?

    36. Subnet y Route Table¶

    Cada subnet debe utilizar la Route Table prevista.

    Nuestro diseño:

    SUBNET-WEB
→ RT-WEB-PUBLIC

SUBNET-APP
→ RT-APP-PRIVATE

SUBNET-DB
→ RT-DB-ISOLATED

    37. Error especialmente peligroso¶

    SUBNET-DB
→ RT-APP-PRIVATE

    puede no producir una caída.

    Puede producir:

    DB → Internet

    cuando no debería.

    Es un fallo de seguridad por:

    exceso de conectividad

    38. Leer la Route Table¶

    No basta con ver que existe una ruta.

    Debemos preguntar:

    ¿Qué ruta coincide con este destino?

    APP → DB:

    10.0.0.0/16 → local

    APP → Internet:

    0.0.0.0/0 → NAT Gateway

    39. Longest Prefix Match¶

    Si:

    10.0.0.0/16 → local
0.0.0.0/0 → NAT

    para:

    10.0.30.10

    se utiliza:

    local

    No NAT.

    40. WEB e Internet Gateway¶

    Para conectividad pública IPv4 comprobar:

    SUBNET-WEB
↓
RT-WEB-PUBLIC
↓
0.0.0.0/0 → IGW
↓
IGW asociado a VPC

    y, para una EC2 directamente pública:

    public IPv4/EIP
+
Security Group

    41. Public subnet no implica public EC2¶

    Podemos tener:

    subnet pública ✓
route to IGW ✓
EC2 public IPv4 ✕

    Resultado:

    la EC2 no tiene conectividad pública IPv4 directa

    42. APP e Internet¶

    Packet path:

    EC2-APP
   ↓
SUBNET-APP
   ↓
RT-APP-PRIVATE
   ↓
0.0.0.0/0
   ↓
NAT Gateway
   ↓
SUBNET-WEB
   ↓
RT-WEB-PUBLIC
   ↓
IGW
   ↓
Internet

    43. Diagnóstico NAT Gateway¶

    Comprobar:

    1. APP está en SUBNET-APP
2. SUBNET-APP → RT-APP-PRIVATE
3. 0.0.0.0/0 → NAT
4. NAT Gateway = Available
5. NAT en subnet pública
6. subnet pública → 0.0.0.0/0 → IGW
7. IGW asociado
8. SG/NACL
9. DNS/aplicación

    44. Security Groups¶

    Para:

    WEB → APP:8080

    revisar:

    EC2-WEB → SG-WEB
EC2-APP → SG-APP

    y:

    SG-APP
Inbound
TCP/8080
Source = SG-WEB

    45. Referencia SG¶

    Una regla:

    Source = SG-WEB

    no significa:

    todo 10.0.10.0/24

    Expresa:

    recursos asociados al rol SG-WEB

    46. Security Groups son stateful¶

    Si WEB inicia:

    WEB:ephemeral
→ APP:8080

    la respuesta pertenece al estado de la conexión.

    No necesitamos una regla inbound inversa para el puerto efímero de WEB.

    47. NACL¶

    Las Network ACL son:

    stateless

    Por tanto debemos analizar:

    ida
+
retorno

    independientemente.

    48. Fallo clásico NACL¶

    Tenemos:

    WEB → APP:8080

    NACL APP inbound:

    ALLOW TCP/8080
from 10.0.10.0/24

    Pero outbound no permite correctamente el retorno hacia el puerto efímero del cliente.

    Resultado:

    SG ✓
routing ✓
service ✓
session ✕

    49. Diagnóstico¶

    Pensar:

    WEB:53124
→ APP:8080

    Respuesta:

    APP:8080
→ WEB:53124

    La NACL debe permitir ambos sentidos según su política.

    50. Orden NACL¶

    Ejemplo correcto:

    90  DENY 10.0.10.50/32
100 ALLOW 10.0.10.0/24

    Ejemplo problemático:

    100 ALLOW 10.0.10.0/24
200 DENY 10.0.10.50/32

    Si la primera regla ya coincide:

    la posterior no corrige la decisión

    51. Árbol rápido AWS¶

    ¿EC2 correcta y activa?
   │
   ├── NO → recurso
   │
   └── SÍ
        ↓
¿Subnet correcta?
   │
   ├── NO → placement
   │
   └── SÍ
        ↓
¿Route Table correcta?
   │
   ├── NO → asociación/routing
   │
   └── SÍ
        ↓
¿Existe ruta adecuada?
   │
   ├── NO → routing
   │
   └── SÍ
        ↓
¿Target operativo?
   │
   ├── NO → IGW/NAT/etc.
   │
   └── SÍ
        ↓
¿SG permite?
   │
   ├── NO → política recurso
   │
   └── SÍ
        ↓
¿NACL permite ida y retorno?
   │
   ├── NO → política subnet
   │
   └── SÍ
        ↓
¿Servicio escucha?
   │
   ├── NO → SO/aplicación
   │
   └── SÍ → flujo funcional

    52. Matriz de síntomas¶

    Síntoma Primera comprobación Después
    misma VLAN no comunica VLAN/bridge/IP ARP/FDB
    VLAN diferentes no comunican gateway/routing firewall
    WEB→APP:8080 falla servicio/routing firewall/SG/NACL
    ping falla, curl funciona política ICMP no corregir TCP
    APP sin Internet on-premise gateway/IP externa firewall/NAT
    IP externa funciona, nombre no DNS resolver
    AWS APP sin Internet RT privada NAT/IGW
    AWS WEB no pública public IPv4 + RT IGW/SG
    AWS WEB→APP falla SG-APP NACL/service
    ida parece correcta pero timeout retorno NACL/state
    DB tiene Internet y no debería Route Table SG/NACL/egress

    54. Herramientas AWS¶

    Dependiendo del entorno y de los servicios habilitados:

    EC2 network configuration
VPC
Subnets
Route Tables
Internet Gateway
NAT Gateway
Security Groups
Network ACL
VPC Flow Logs
Reachability Analyzer
CloudWatch

    No todas son necesarias para cada incidencia.

    La herramienta se selecciona según la hipótesis.

    55. VPC Flow Logs¶

    Cuando estén habilitados, pueden ayudar a observar información del tráfico de red.

    Son especialmente útiles para complementar:

    SG
NACL
routing

    pero no sustituyen el razonamiento del packet path.

    56. Reachability Analyzer¶

    Puede utilizarse como herramienta complementaria para analizar la configuración del camino entre recursos.

    Pero el objetivo docente sigue siendo que el alumnado pueda explicar:

    source
destination
path
routing
security controls

    sin depender exclusivamente de una herramienta automática.

    57. No confundir herramienta con diagnóstico¶

    tcpdump
Flow Logs
Firewall Log
Reachability Analyzer

    proporcionan:

    EVIDENCIAS

    La causa raíz la obtenemos interpretando esas evidencias dentro de la arquitectura.

    58. Método de aislamiento binario¶

    Cuando el recorrido es largo podemos buscar el punto de ruptura.

    Ejemplo:

    A ─ B ─ C ─ D ─ E

    Si sabemos:

    A → C ✓

    pero:

    A → E ✕

    investigamos:

    C → D → E

    No volvemos continuamente a A.

    59. Cambiar una sola variable¶

    Durante troubleshooting:

    HIPÓTESIS
   ↓
CAMBIO
   ↓
PRUEBA

    No:

    cambiar ruta
+
firewall
+
DNS
+
reiniciar

    porque si funciona después:

    no sabremos por qué

    60. Corrección mínima¶

    La mejor solución no es:

    la que devuelve conectividad

    sino:

    la que corrige la causa raíz
sin ampliar innecesariamente
la superficie de comunicación

    61. Ejemplo¶

    Problema:

    WEB → APP:8080 ✕

    Solución incorrecta:

    WEB → any → any → PASS

    Solución correcta:

    WEB → APP → TCP/8080 → PASS

    si esa era la causa.

    62. Validar después de corregir¶

    Siempre:

    PRUEBA POSITIVA
+
PRUEBA NEGATIVA

    Ejemplo:

    WEB → APP:8080 ✓
WEB → DB:5432  ✕

    Si solo comprobamos la positiva podríamos haber creado una regla excesivamente amplia.

    63. Causa raíz frente a síntoma¶

    Ejemplo:

    síntoma:
APP no tiene Internet

    No es una causa raíz.

    Posibles causas:

    gateway incorrecto
firewall
NAT
WAN
Route Table
NAT Gateway
NACL
DNS

    64. Informe RCA¶

    Cada incidencia importante debe documentarse:

    Campo Contenido
    Requisito esperado
    Síntoma
    Alcance
    Packet path esperado
    Hipótesis inicial
    Primera evidencia
    Hipótesis descartadas
    Evidencia decisiva
    Causa raíz
    Corrección mínima
    Prueba positiva
    Prueba negativa
    Riesgo residual

    65. Ejemplo RCA¶

    Síntoma¶

    WEB no accede a APP:8080

    Evidencia 1¶

    WEB → gateway ✓

    Descartamos parcialmente:

    VLAN10
gateway WEB

    Evidencia 2¶

    APP escucha TCP/8080 ✓

    Evidencia 3¶

    Firewall Log:

    BLOCK
WEB → APP:8080

    Causa raíz¶

    regla WEB_to_APP configurada
con destino TCP/8081

    Corrección¶

    8081 → 8080

    Validación positiva¶

    WEB → APP:8080 ✓

    Validación negativa¶

    WEB → DB:5432 ✕

    66. Escenarios rápidos¶

    Escenario A¶

    WEB no alcanza APP
ip route get muestra 10.10.20.10 dev eth0

    cuando WEB tiene:

    10.10.10.10/8

    Hipótesis:

    máscara incorrecta

    Escenario B¶

    APP alcanza 1.1.1.1
APP no resuelve example.com

    Hipótesis:

    Conclusión¶

    Un buen administrador de red no memoriza únicamente configuraciones.

    Debe ser capaz de responder:

    ¿qué debería ocurrir?
¿por dónde debería pasar?
¿qué componente decide?
¿qué evidencia tengo?
¿dónde desaparece el tráfico?
¿por qué?

    Por eso, nuestra metodología durante toda la unidad será:

    PREDECIR
   ↓
OBSERVAR
   ↓
AISLAR
   ↓
FORMULAR HIPÓTESIS
   ↓
OBTENER EVIDENCIA
   ↓
IDENTIFICAR CAUSA RAÍZ
   ↓
APLICAR CAMBIO MÍNIMO
   ↓
VALIDAR POSITIVO
   ↓
VALIDAR NEGATIVO
   ↓
DOCUMENTAR

    Troubleshooting no consiste en conseguir que vuelva a funcionar. Consiste en demostrar por qué dejó de funcionar y corregir exactamente esa causa.
