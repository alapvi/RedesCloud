    OPNsense · Router y firewall virtual¶

    Ahora convertimos la segmentación creada en Proxmox en una arquitectura enrutable mediante OPNsense.

    1. Objetivo¶

    Partimos de tres segmentos independientes:

    VLAN 10 → WEB → 10.10.10.0/24
VLAN 20 → APP → 10.10.20.0/24
VLAN 30 → DB  → 10.10.30.0/24

    Todavía tenemos:

    3 VLAN + 3 redes IP + 0 routers

    Introducimos OPNsense para proporcionar:

    routing inter-VLAN
+
gateway de cada red
+
conectividad WAN

    La política restrictiva se implementará después. Primero debemos demostrar que el routing funciona.

    2. Arquitectura¶

                             RED DEL AULA
                      DHCP + acceso Internet
                              │
                            vmbr0
                              │
                            WAN
                              │
                     ┌────────┴────────┐
                     │    OPNsense     │
                     │ Router/Firewall │
                     └────────┬────────┘
                              │
                         TRUNK 802.1Q
                              │
                       vmbr1 VLAN-aware
              ┌───────────────┼───────────────┐
              │               │               │
           VLAN 10         VLAN 20         VLAN 30
              │               │               │
             WEB             APP              DB

    3. Separación de funciones¶

    Proxmox
→ virtualiza
→ conmuta
→ transporta VLAN

    OPNsense
→ enruta
→ filtra
→ realiza NAT

    No utilizaremos el host Proxmox como router de laboratorio. Esto mantiene separado el plano de gestión del hipervisor de la función de routing/firewall que queremos estudiar.

    4. VM OPNsense¶

    Una configuración razonable:

    CPU: 2 vCPU
RAM: 2–4 GB
Disco: 16–20 GB
NIC: 2

    La primera vNIC es WAN; la segunda es trunk.

    5. WAN¶

    En Proxmox:

    Bridge: vmbr0
VLAN Tag: vacío

    En OPNsense:

    IPv4 Configuration Type: DHCP

    El router del aula entregará:

    IP + máscara + gateway + DNS

    6. Particularidades del aula¶

    WAN con IP privada¶

    La red del aula probablemente utiliza RFC1918. Si OPNsense aplica bloqueo de redes privadas sobre WAN, debemos revisar esa opción para este escenario de laboratorio.

    Varias MAC tras el mismo puerto físico¶

    El puerto físico verá al menos:

    MAC Proxmox
MAC OPNsense WAN

    Si el switch aplica port-security de una sola MAC, la WAN de OPNsense puede fallar aunque la configuración virtual sea correcta.

    Este es un excelente ejemplo de problema situado fuera del hipervisor.

    7. Trunk interno¶

    Segunda vNIC:

    Bridge: vmbr1
VLAN Tag: vacío

    Debe transportar simultáneamente:

    VLAN 10
VLAN 20
VLAN 30

    No asignaremos una IP normal a la interfaz padre si se utiliza únicamente como contenedor del trunk.

    8. Crear VLAN en OPNsense¶

    Sobre la interfaz padre interna:

    VLAN10_WEB → VID 10
VLAN20_APP → VID 20
VLAN30_DB  → VID 30

    Después se asignan como interfaces lógicas.

    9. Direccionamiento de OPNsense¶

    WEB → 10.10.10.1/24
APP → 10.10.20.1/24
DB  → 10.10.30.1/24

    No se configura un gateway upstream en estas interfaces internas.

    10. Configurar los hosts¶

    WEB
IP 10.10.10.10/24
GW 10.10.10.1

APP
IP 10.10.20.10/24
GW 10.10.20.1

DB
IP 10.10.30.10/24
GW 10.10.30.1

    11. Redes directamente conectadas¶

    OPNsense participa en las tres redes, por tanto conoce automáticamente:

    10.10.10.0/24 → WEB
10.10.20.0/24 → APP
10.10.30.0/24 → DB

    No necesitamos rutas estáticas para comunicar estas tres subnets.

    12. Primero validar el gateway¶

    Desde WEB:

    ping -c 4 10.10.10.1

    Desde APP:

    ping -c 4 10.10.20.1

    Desde DB:

    ping -c 4 10.10.30.1

    Si una VM no llega a su gateway, todavía no investigamos routing inter-VLAN.

    13. Routing frente a firewall¶

    OPNsense es router y firewall.

    ROUTING
→ ¿existe camino?

FIREWALL
→ ¿está permitido usarlo?

    Las interfaces nuevas pueden no disponer de reglas permisivas. Por ello, para demostrar routing podemos crear temporalmente reglas explícitas de laboratorio que permitan tráfico entre las redes.

    WEB → any → PASS temporal
APP → any → PASS temporal
DB  → any → PASS temporal

    Estas reglas no son la política final.

    14. Validar routing inter-VLAN¶

    Ejemplo WEB→APP:

    ping -c 4 10.10.20.10

    Recorrido esperado:

    WEB
 ↓
GW 10.10.10.1
 ↓
OPNsense
 ↓
VLAN20
 ↓
APP

    15. NAT automático¶

    OPNsense puede generar automáticamente reglas de Outbound NAT para redes internas.

    En este capítulo el acceso a Internet desde WEB/APP/DB no es el objetivo.

    Si una VM ya consigue salir a Internet, debemos identificar que la traducción está ocurriendo y no confundirla con routing puro.

    16. Fallos provocados¶

    • VLAN creada sobre interfaz padre incorrecta.
    • vNIC trunk etiquetada con VLAN 10 en Proxmox.
    • gateway incorrecto.
    • interfaz VLAN deshabilitada.
    • regla temporal ausente.
    • WAN privada bloqueada.
    • port-security físico.

    17. Cadena de troubleshooting¶

    VM

    1. dos vNIC de OPNsense;
    2. WAN DHCP;
    3. VLAN 10/20/30;
    4. interfaces WEB/APP/DB;
    5. IP de cada interfaz;
    6. gateways de las VM;
    7. reachability de cada gateway;
    8. routing inter-VLAN;
    9. explicación de un fallo provocado.

    Primero demostramos que existe un camino. Después decidiremos quién tiene derecho a utilizarlo.
