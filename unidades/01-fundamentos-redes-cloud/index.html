    Introducción al networking en Proxmox VE¶

    Bloque 1 de 4: Introducción al networking · Networking avanzado · VPN · Escenarios avanzados de uso

    0. Ficha de la unidad¶

    Finalidad¶

    Esta unidad introduce el modelo de red de Proxmox Virtual Environment (Proxmox VE) mediante una combinación de explicación conceptual, observación del sistema y prácticas guiadas. El objetivo no es memorizar opciones de la interfaz, sino comprender cómo circula una trama desde una máquina virtual hasta otra máquina o hasta la red física.

    Al finalizar, el alumnado deberá ser capaz de:

    1. Identificar las interfaces físicas y virtuales de un nodo Proxmox.
    2. Explicar la función de un Linux bridge y compararlo con un switch Ethernet.
    3. Interpretar una configuración básica de /etc/network/interfaces.
    4. Crear una red virtual aislada para máquinas virtuales y contenedores.
    5. Conectar una máquina virtual a una red externa cuando el laboratorio lo permita.
    6. Seleccionar el modelo de tarjeta virtual adecuado.
    7. Verificar conectividad con herramientas de Linux.
    8. Aplicar un procedimiento sistemático de diagnóstico ante fallos de red.
    9. Documentar una topología mediante un esquema, una tabla de direccionamiento y evidencias de funcionamiento.

    Conocimientos previos recomendados¶

    • Direccionamiento IPv4 y notación CIDR.
    • Diferencia entre dirección IP, máscara, puerta de enlace y DNS.
    • Conceptos básicos de Ethernet, MAC, switch, router y broadcast.
    • Manejo elemental de la terminal Linux.
    • Creación básica de máquinas virtuales en Proxmox VE.

    Distribución temporal orientativa¶

    Sesión Contenido Duración
    1 Modelo de red de Proxmox y recorrido de los paquetes 1 h
    2 Interfaces físicas, bridges e interfaces virtuales 1 h
    3 Lectura de la configuración y herramientas de diagnóstico 1 h
    4 Práctica 1: inventario y análisis de la red inicial 1 h
    5-6 Práctica 2: creación de una red virtual aislada 2 h
    7 Práctica 3: conexión controlada a una red externa 1-2 h
    8 Resolución de incidencias y reto final 1-2 h

    1. Escenario de laboratorio¶

    El material está diseñado para poder utilizarse en dos tipos de entorno:

    Escenario A. Proxmox instalado directamente sobre un servidor físico¶

    El nodo Proxmox dispone de una o varias tarjetas de red físicas. Una de ellas se utiliza normalmente para:

    • administrar el nodo;
    • acceder a la interfaz web;
    • conectar máquinas virtuales a la red del aula;
    • proporcionar acceso a otros servicios de infraestructura.

    Escenario B. Proxmox virtualizado para cada alumno¶

    Cada alumno dispone de una máquina virtual que ejecuta Proxmox VE. Este modelo se conoce como virtualización anidada o nested virtualization.

    En este caso:

    • la “tarjeta física” que ve el Proxmox del alumno es, en realidad, una tarjeta virtual proporcionada por el hipervisor principal;
    • las interfaces pueden aparecer como ens18, ens19, enp6s18 u otros nombres predecibles de Linux;
    • las máquinas virtuales creadas dentro de ese Proxmox generan un segundo nivel de interfaces virtuales;
    • la salida directa de las máquinas internas hacia la red del centro dependerá de la configuración del hipervisor principal, de los filtros de MAC y de la política de seguridad del laboratorio.

    Recomendación docente: las primeras prácticas deben realizarse sobre bridges aislados. De esta forma, diez alumnos pueden crear sus propias topologías sin introducir direcciones IP, servidores DHCP o tráfico no controlado en la red real del centro.

    Recursos mínimos por alumno¶

    Configuración orientativa para el Proxmox anidado:

    • 4 vCPU.
    • 12-16 GB de RAM.
    • 80-100 GB de disco con aprovisionamiento fino.
    • 1 interfaz para gestión.
    • Una segunda interfaz virtual opcional para prácticas de conexión externa.
    • Dos máquinas virtuales Linux ligeras para las pruebas.

    2. El problema que resuelve el networking de un hipervisor¶

    En un equipo físico convencional, el sistema operativo utiliza una tarjeta de red para enviar y recibir datos. En un hipervisor aparecen nuevas preguntas:

    • ¿Cómo puede compartir una tarjeta física un conjunto de máquinas virtuales?
    • ¿Cómo se conectan dos máquinas virtuales sin salir del servidor?
    • ¿Cómo se aísla una red de laboratorio de la red del centro?
    • ¿Dónde se coloca la dirección IP de administración del hipervisor?
    • ¿Cómo se conectan máquinas virtuales a varias redes?

    Proxmox VE utiliza normalmente un modelo de red en puente. El elemento central es un Linux bridge, que realiza una función equivalente a la de un switch Ethernet software.

    Una primera representación sería:

                             NODO PROXMOX

 Red física                                      Máquinas virtuales
     │
     │ cable o enlace virtual
     ▼
┌──────────┐       ┌──────────────────┐       ┌──────────────┐
│   eno1   │──────▶│      vmbr0       │◀──────│ tap100i0     │
│ NIC host │       │  bridge Linux    │       │ NIC de VM100 │
└──────────┘       │  "switch virtual"│       └──────┬───────┘
                   │                  │              │
                   │                  │       ┌──────▼───────┐
                   │                  │       │ Sistema VM100│
                   └─────────▲────────┘       └──────────────┘
                             │
                      ┌──────┴───────┐
                      │ tap101i0     │
                      │ NIC de VM101 │
                      └──────────────┘

    El bridge aprende direcciones MAC y reenvía tramas entre sus puertos, de forma parecida a un switch físico.

    3. Componentes de red en Proxmox VE¶

    3.1. Interfaz de red física¶

    Es la interfaz asociada a una tarjeta de red del servidor. Algunos nombres habituales son:

    • eno1, eno2: interfaces integradas en placa o identificadas por firmware;
    • enp3s0, enp4s0f1: interfaces identificadas por su posición PCI;
    • ens18: nombre frecuente en máquinas virtuales;
    • eth0: nomenclatura clásica, menos habitual en instalaciones modernas.

    Podemos consultar las interfaces con:

    ip -br link

    Ejemplo de salida:

    lo               UNKNOWN        00:00:00:00:00:00
ens18            UP             bc:24:11:7a:20:10
vmbr0            UP             bc:24:11:7a:20:10

    La interfaz física suele configurarse con inet manual cuando forma parte de un bridge. La dirección IP de administración se configura en el bridge, no en el puerto físico que ha sido incorporado a él.

    3.2. Linux bridge¶

    Un Linux bridge es un switch Ethernet implementado por software en el kernel de Linux. En Proxmox suele recibir nombres como:

    • vmbr0;
    • vmbr1;
    • vmbr2.

    Cada bridge crea un dominio de capa 2 independiente, salvo que se conecte a otros bridges, a una interfaz física o a un dispositivo de encaminamiento.

    Un bridge puede utilizarse de tres formas básicas:

    A. Bridge conectado a una interfaz física¶

    VM ── vmbr0 ── ens18 ── red externa

    Permite que las máquinas virtuales participen, si la infraestructura lo admite, en la red externa conectada a esa interfaz.

    B. Bridge aislado¶

    VM1 ──┐
      ├── vmbr1
VM2 ──┘

    No tiene puerto físico. Las máquinas conectadas pueden comunicarse entre sí, pero no salen de esa red sin un router o una configuración adicional.

    C. Bridge con dirección IP del host¶

    Host Proxmox 10.20.10.1
            │
VM1 ───── vmbr1 ───── VM2

    El propio nodo Proxmox participa en la red. Es útil para administración, pruebas, encaminamiento o servicios concretos, aunque debe utilizarse de forma planificada.

    3.3. Interfaces virtuales de máquinas KVM¶

    Cuando una máquina virtual está encendida, Proxmox crea interfaces tap en el host. Un ejemplo es:

    tap100i0

    Su nombre puede interpretarse así:

    • 100: identificador de la máquina virtual;
    • i0: primera interfaz de red de esa máquina.

    Esta interfaz actúa como el extremo del cable virtual que conecta la tarjeta de la VM con el bridge.

    3.4. Interfaces virtuales de contenedores LXC¶

    Los contenedores utilizan normalmente pares de interfaces virtuales veth. Un extremo queda en el host y el otro aparece dentro del espacio de red del contenedor.

    La idea funcional es la misma:

    Contenedor ── veth ── vmbrX

    3.5. Tarjeta de red que ve el sistema invitado¶

    Al añadir una interfaz a una VM, Proxmox permite seleccionar un modelo de hardware virtual. Los más comunes son:

    Modelo Uso recomendado
    VirtIO Opción preferente para Linux moderno y Windows con controladores VirtIO. Buen rendimiento y bajo consumo de CPU.
    E1000 Emulación de una tarjeta Intel. Útil por compatibilidad con sistemas que no disponen de VirtIO.
    VMXNET3 Puede ser útil en algunos sistemas con controladores compatibles.
    Realtek RTL8139 Compatibilidad con sistemas antiguos; no es la opción habitual para nuevas máquinas.

    Para las prácticas del curso se utilizará VirtIO, salvo que el sistema invitado no disponga del controlador necesario.

    3.6. Dirección MAC¶

    Cada interfaz virtual necesita una dirección MAC única dentro del dominio de capa 2. Proxmox puede generarla automáticamente.

    La MAC permite que el bridge aprenda en qué puerto se encuentra cada sistema. Puede consultarse con:

    bridge fdb show br vmbr0

    La tabla FDB (Forwarding Database) de un bridge cumple una función semejante a la tabla MAC de un switch.

    3.7. Dirección IP, gateway y DNS¶

    Proxmox conecta interfaces en capa 2, pero la configuración IP de la VM depende normalmente del sistema operativo invitado.

    Conviene separar claramente:

    Elemento Función
    Dirección MAC Identifica la interfaz dentro de la red Ethernet.
    Dirección IP Identifica lógicamente al equipo en una red IP.
    Máscara/prefijo Determina qué destinos se consideran locales.
    Gateway Router utilizado para llegar a otras redes.
    DNS Traduce nombres a direcciones IP.

    Regla esencial: dos equipos de la misma subred pueden comunicarse a través del bridge sin gateway. El gateway solo es necesario para alcanzar redes diferentes.

    4. Recorrido de una trama¶

    Supongamos dos máquinas virtuales conectadas a vmbr1:

    • vm-a: 10.20.10.11/24;
    • vm-b: 10.20.10.12/24.

    Cuando vm-a ejecuta:

    ping 10.20.10.12

    ocurre, de forma simplificada, lo siguiente:

    1. vm-a comprueba que 10.20.10.12 pertenece a su subred local.
    2. Si desconoce la MAC de vm-b, envía una solicitud ARP en broadcast.
    3. La trama entra en la interfaz virtual asociada a vm-a.
    4. vmbr1 reenvía el broadcast a los demás puertos del bridge.
    5. vm-b responde indicando su dirección MAC.
    6. Ambas máquinas almacenan temporalmente la relación IP-MAC.
    7. Los paquetes ICMP posteriores viajan como tramas unicast entre ambos puertos del bridge.

    La trama no necesita salir por una interfaz física. Toda la comunicación puede permanecer dentro del nodo Proxmox.

    Podemos observar el tráfico desde el host con:

    tcpdump -eni vmbr1 arp or icmp

    5. Configuración de red del nodo¶

    Proxmox permite administrar la red desde:

    1. la interfaz web;
    2. la consola o SSH;
    3. el archivo /etc/network/interfaces.

    5.1. Interfaz web¶

    Ruta habitual:

    Nodo Proxmox → System → Network

    Desde esta pantalla se pueden crear o editar:

    • Linux bridges;
    • bonds;
    • VLAN;
    • interfaces de red;
    • otros tipos de dispositivos soportados.

    Tras guardar cambios, Proxmox muestra la configuración pendiente. En instalaciones modernas con ifupdown2, la opción Apply Configuration permite aplicar muchos cambios sin reiniciar el nodo.

    Advertencia: una configuración incorrecta de la interfaz de administración puede cortar el acceso web y SSH. Las modificaciones importantes deben realizarse con acceso a la consola del nodo o con un mecanismo de recuperación disponible.

    5.2. Archivo /etc/network/interfaces¶

    Una configuración básica puede tener este aspecto:

    auto lo
iface lo inet loopback

iface ens18 inet manual

auto vmbr0
iface vmbr0 inet static
        address 192.168.50.20/24
        gateway 192.168.50.1
        bridge-ports ens18
        bridge-stp off
        bridge-fd 0

source /etc/network/interfaces.d/*

    Lectura línea a línea¶

    auto lo
iface lo inet loopback

    Configura la interfaz de loopback.

    iface ens18 inet manual

    La interfaz ens18 no recibe una configuración IP propia. Se utilizará como puerto del bridge.

    auto vmbr0

    Indica que vmbr0 debe levantarse automáticamente.

    iface vmbr0 inet static

    El bridge tendrá configuración IPv4 estática.

    address 192.168.50.20/24

    Dirección de administración del nodo.

    gateway 192.168.50.1

    Puerta de enlace predeterminada del nodo.

    bridge-ports ens18

    Añade ens18 como puerto del bridge.

    bridge-stp off
bridge-fd 0

    Desactiva STP y establece el retardo de reenvío a cero en este escenario sencillo. En topologías redundantes, estas decisiones deben revisarse.

    Copia de seguridad antes de modificar¶

    cp /etc/network/interfaces \
  /root/interfaces.backup.$(date +%F-%H%M%S)

    Validación visual¶

    cat /etc/network/interfaces

    Aplicación desde consola¶

    ifreload -a

    Esta operación debe realizarse con precaución. Un error de sintaxis o direccionamiento puede dejar inaccesible el nodo.

    6. Herramientas básicas de observación y diagnóstico¶

    6.1. Estado resumido de interfaces¶

    ip -br link
ip -br address

    Permiten comprobar rápidamente:

    • nombre de la interfaz;
    • estado UP o DOWN;
    • dirección MAC;
    • direcciones IP asignadas.

    6.2. Tabla de rutas¶

    ip route

    Ejemplo:

    default via 192.168.50.1 dev vmbr0
192.168.50.0/24 dev vmbr0 proto kernel scope link src 192.168.50.20

    Interpretación:

    • el tráfico a 192.168.50.0/24 se entrega directamente por vmbr0;
    • el resto se envía al gateway 192.168.50.1.

    6.3. Puertos de los bridges¶

    bridge link

    También puede utilizarse:

    ip link show master vmbr0

    6.4. Tabla MAC del bridge¶

    bridge fdb show br vmbr0

    6.5. Vecinos ARP/ND¶

    ip neigh

    6.6. Pruebas de conectividad¶

    ping -c 4 DIRECCION_IP

    Para observar la ruta:

    traceroute DIRECCION_IP

    Si traceroute no está instalado, puede utilizarse:

    tracepath DIRECCION_IP

    6.7. Captura de tráfico¶

    tcpdump -eni vmbr1

    Filtros útiles:

    tcpdump -eni vmbr1 arp
tcpdump -eni vmbr1 icmp
tcpdump -eni vmbr1 'host 10.20.10.11'
tcpdump -eni vmbr1 'port 53'

    6.8. Configuración de red de una VM o contenedor¶

    qm config 100
pct config 200

    Para mostrar solo las interfaces:

    qm config 100 | grep '^net'
pct config 200 | grep '^net'

    8. Práctica guiada 2: red virtual aislada¶

    8.1. Objetivos¶

    • Crear un bridge sin interfaz física.
    • Conectar dos máquinas virtuales a la misma red aislada.
    • Configurar direccionamiento IPv4.
    • Comprobar ARP e ICMP.
    • Capturar tráfico desde el nodo Proxmox.

    8.2. Topología¶

    flowchart LR
    VM1[vm-a<br/>10.20.10.11/24] --- BR[vmbr1<br/>bridge aislado]
    VM2[vm-b<br/>10.20.10.12/24] --- BR

    Características:

    • Red: 10.20.10.0/24.
    • No se configura gateway.
    • No se configura DNS.
    • El bridge no tiene puerto físico.
    • El nodo Proxmox no necesita dirección IP en vmbr1 para que las dos VMs se comuniquen.

    8.3. Paso 0. Preparar las máquinas¶

    Se necesitan dos VMs Linux ligeras. Ejemplo:

    VM VMID RAM vCPU Disco Interfaz
    vm-a 110 1-2 GB 1 8-16 GB VirtIO
    vm-b 120 1-2 GB 1 8-16 GB VirtIO

    Pueden utilizarse clones vinculados de una plantilla para reducir consumo de disco y tiempo de despliegue.

    8.4. Paso 1. Crear vmbr1 desde la interfaz web¶

    Ruta:

    Nodo → System → Network → Create → Linux Bridge

    Valores:

    Campo Valor
    Name vmbr1
    IPv4/CIDR vacío
    Gateway IPv4 vacío
    Bridge ports vacío
    Autostart activado
    VLAN aware desactivado para esta práctica
    Comment Red aislada laboratorio

    Guarda la configuración y revisa los cambios pendientes.

    8.5. Paso 2. Revisar la configuración generada¶

    El fragmento esperado es equivalente a:

    auto vmbr1
iface vmbr1 inet manual
        bridge-ports none
        bridge-stp off
        bridge-fd 0
        # Red aislada laboratorio

    Aplica la configuración desde la interfaz web. Mantén disponible la consola por si se produce un error.

    8.6. Paso 3. Verificar el bridge¶

    ip -br link show vmbr1

    También:

    bridge link

    Antes de encender las VMs, vmbr1 puede no mostrar interfaces tap asociadas.

    8.7. Paso 4. Conectar las máquinas virtuales¶

    Para cada VM:

    VM → Hardware → Add → Network Device

    Selecciona:

    Campo Valor
    Bridge vmbr1
    Model VirtIO (paravirtualized)
    VLAN Tag vacío
    Firewall según política del laboratorio; para la primera prueba puede mantenerse sin reglas específicas

    Si la VM tenía otra interfaz y no se necesita, puede retirarse o mantenerse claramente identificada. Para evitar confusiones en la práctica inicial, es preferible que cada VM tenga una sola NIC conectada a vmbr1.

    8.8. Paso 5. Encender las VMs y observar interfaces tap¶

    En el nodo:

    ip -br link | grep tap
bridge link

    Deberían aparecer interfaces semejantes a:

    tap110i0
 tap120i0

    Comprueba que ambas pertenecen a vmbr1.

    8.9. Paso 6. Configurar IP temporal dentro de las VMs¶

    Primero identifica la interfaz:

    ip -br link

    En vm-a:

    sudo ip link set dev ens18 up
sudo ip address add 10.20.10.11/24 dev ens18

    En vm-b:

    sudo ip link set dev ens18 up
sudo ip address add 10.20.10.12/24 dev ens18

    El nombre de la interfaz dentro de la VM puede ser diferente. Sustituye ens18 por el nombre real.

    Comprueba:

    ip -br addr
ip route

    La configuración realizada con ip address add es temporal y se perderá al reiniciar. Esto resulta útil para una primera prueba porque evita depender del gestor de red de cada distribución.

    8.10. Paso 7. Probar conectividad¶

    Desde vm-a:

    ping -c 4 10.20.10.12

    Desde vm-b:

    ping -c 4 10.20.10.11

    Resultado esperado: respuesta correcta en ambos sentidos.

    8.11. Paso 8. Consultar la tabla de vecinos¶

    Dentro de cada VM:

    ip neigh

    Deberá aparecer la IP de la otra VM asociada a una dirección MAC.

    8.12. Paso 9. Observar ARP e ICMP desde Proxmox¶

    En el nodo Proxmox:

    tcpdump -eni vmbr1 arp or icmp

    Limpia antes la entrada ARP de una VM para volver a observar el proceso:

    sudo ip neigh flush dev ens18

    Después repite el ping.

    Identifica en la captura:

    1. solicitud ARP;
    2. respuesta ARP;
    3. ICMP echo request;
    4. ICMP echo reply.

    8.13. Paso 10. Verificar aprendizaje de MAC¶

    En Proxmox:

    bridge fdb show br vmbr1

    Relaciona las MAC aprendidas con las MAC mostradas en la configuración de cada VM.

    8.14. Configuración persistente en Debian mediante systemd-networkd¶

    Ejemplo para vm-a, si la distribución utiliza systemd-networkd:

    # /etc/systemd/network/20-lab.network
[Match]
Name=ens18

[Network]
Address=10.20.10.11/24

    Después:

    sudo systemctl restart systemd-networkd

    En vm-b, cambia la dirección a 10.20.10.12/24.

    La forma de persistir la red cambia según la distribución: NetworkManager, Netplan, /etc/network/interfaces o systemd-networkd. El profesorado debe adaptar este apartado a la imagen base empleada.

    9. Práctica guiada 3: conexión controlada a una red externa¶

    9.1. Finalidad¶

    Esta práctica permite comprender cómo un bridge enlaza las máquinas virtuales con una red situada fuera del nodo Proxmox.

    Solo debe realizarse en una red de laboratorio autorizada. No debe conectarse una VM directamente a la red corporativa o educativa sin conocer la política de direccionamiento, DHCP, filtrado de MAC, VLAN y seguridad.

    9.2. Topología¶

    flowchart LR
    VM[VM Linux] --- BR[vmbr0]
    BR --- NIC[ens18]
    NIC --- LAB[Red externa de laboratorio]
    LAB --- GW[Gateway / DHCP]

    9.3. Comprobaciones previas¶

    El docente debe confirmar:

    • que vmbr0 está conectado a la red adecuada;
    • que la red permite las MAC de las VMs internas;
    • que existe un rango de direcciones reservado o un DHCP de laboratorio;
    • que no se producirá conflicto con la red del centro;
    • que el hipervisor exterior permite el tráfico de las MAC anidadas, si se usa virtualización anidada.

    9.4. Paso 1. Examinar vmbr0¶

    ip -br addr show vmbr0
ip link show master vmbr0
ip route

    Confirma que el puerto físico o virtual correcto pertenece al bridge.

    9.5. Paso 2. Conectar una VM¶

    En la VM:

    Hardware → Add → Network Device
    • Bridge: vmbr0.
    • Model: VirtIO.
    • VLAN Tag: vacío, salvo indicación del docente.

    9.6. Paso 3A. Obtener dirección por DHCP¶

    Dentro de la VM, según distribución:

    sudo dhclient -v ens18

    O activa el perfil DHCP del gestor de red correspondiente.

    Comprueba:

    ip -br addr
ip route
cat /etc/resolv.conf

    9.7. Paso 3B. Configuración estática¶

    Ejemplo exclusivamente ilustrativo:

    IP:       192.168.60.51/24
Gateway:  192.168.60.1
DNS:      192.168.60.1

    El direccionamiento real debe proporcionarlo el docente.

    9.8. Paso 4. Pruebas por niveles¶

    Realiza las pruebas en este orden:

    Nivel 1. Enlace e interfaz¶

    ip -br link

    Nivel 2. Dirección local¶

    ip -br addr

    Nivel 3. Gateway¶

    ping -c 4 192.168.60.1

    Nivel 4. Dirección remota¶

    ping -c 4 1.1.1.1

    Nivel 5. Resolución DNS¶

    getent hosts example.com

    Nivel 6. Servicio de aplicación¶

    curl -I https://example.com

    La secuencia permite separar un fallo de enlace, direccionamiento, ruta, DNS o aplicación.

    9.9. Alternativa segura para entornos anidados¶

    Si no se permite que las VMs internas aparezcan directamente en la red exterior, el docente puede proporcionar:

    • una segunda red virtual cerrada en el hipervisor principal;
    • un router virtual controlado;
    • una VM de servicios con DHCP y DNS de laboratorio;
    • una salida mediante NAT, que se desarrollará en el bloque de networking avanzado.

    10. Diferencia entre red de gestión y redes de máquinas virtuales¶

    En una instalación sencilla, la gestión del nodo y las VMs pueden compartir vmbr0. Sin embargo, conceptualmente deben distinguirse:

    Red Función
    Gestión Interfaz web, SSH, API y administración del nodo.
    Máquinas virtuales Tráfico de las cargas de trabajo.
    Almacenamiento NFS, iSCSI, Ceph u otros servicios de datos.
    Clúster Comunicación entre nodos y Corosync.
    Migración Transferencia de memoria y estado de VMs.
    Copias de seguridad Tráfico hacia Proxmox Backup Server u otro destino.

    En el bloque inicial se utilizarán una red de gestión y una red aislada. La separación mediante interfaces, VLAN, bonds o SDN se tratará posteriormente.

    11. Errores frecuentes¶

    11.1. Asignar la IP a la interfaz física y al bridge¶

    Configuración incorrecta:

    iface ens18 inet static
        address 192.168.50.20/24

auto vmbr0
iface vmbr0 inet static
        address 192.168.50.20/24
        bridge-ports ens18

    Problema: se duplica la configuración de capa 3. Cuando una interfaz se integra como puerto de un bridge, la IP debe estar normalmente en el bridge.

    11.2. Configurar dos gateways predeterminados sin planificación¶

    Un host debe tener una política de encaminamiento coherente. Introducir varios gateways por defecto puede provocar rutas asimétricas o resultados inesperados.

    11.3. Confundir bridge con router¶

    Un bridge conecta equipos en capa 2. No enruta automáticamente entre subredes.

    10.20.10.0/24 ── vmbr1 ── 10.30.10.0/24

    El simple hecho de conectar interfaces a un mismo bridge no sustituye a un router ni corrige una configuración IP incoherente.

    11.4. Añadir gateway a una red aislada¶

    En una red interna sin router no debe inventarse una puerta de enlace. Una IP de gateway inexistente no proporciona conectividad.

    11.5. Configurar dos NIC de una VM en la misma subred¶

    Puede provocar selección de rutas, ARP y respuestas impredecibles. Cada interfaz debe tener una función clara.

    11.6. Olvidar que el firewall puede filtrar tráfico¶

    La configuración puede existir en varios niveles:

    • Datacenter;
    • nodo;
    • VM o contenedor;
    • interfaz virtual;
    • sistema operativo invitado.

    Una prueba de red debe comprobar también las reglas activas.

    11.7. Cambiar la red de gestión sin consola¶

    Si se pierde acceso a la interfaz web, la consola local o la consola del hipervisor exterior será necesaria para recuperar la configuración.

    11.8. No comprobar el nombre real de la interfaz¶

    Los ejemplos pueden utilizar ens18, pero cada instalación puede presentar un nombre diferente.

    11.9. Utilizar una dirección ya ocupada¶

    Antes de asignar una IP estática, debe comprobarse el plan de direccionamiento. En un laboratorio controlado puede emplearse arping como ayuda, aunque no sustituye a una gestión correcta de direcciones.

    arping -D -I ens18 10.20.10.11

    12. Método sistemático de resolución de problemas¶

    Cuando una VM no se comunica, no conviene modificar opciones al azar. Se recomienda avanzar desde la capa inferior hacia la superior.

    Paso 1. Definir el alcance¶

    Preguntas iniciales:

    • ¿Falla una VM o todas?
    • ¿Falla solo Internet o tampoco funciona la red local?
    • ¿El problema comenzó después de un cambio?
    • ¿Afecta a IPv4, IPv6 o ambos?
    • ¿La VM está conectada al bridge correcto?

    Paso 2. Comprobar el estado de la interfaz dentro de la VM¶

    ip -br link

    Debe estar UP.

    Paso 3. Comprobar direccionamiento¶

    ip -br addr

    Verifica IP y prefijo.

    Paso 4. Comprobar rutas¶

    ip route

    Para red local no hace falta gateway. Para redes remotas debe existir una ruta adecuada.

    Paso 5. Comprobar la configuración de Proxmox¶

    qm config VMID | grep '^net'

    Revisa:

    • bridge;
    • modelo;
    • MAC;
    • etiqueta VLAN, si existiera;
    • firewall.

    Paso 6. Comprobar el puerto virtual en el host¶

    bridge link

    La interfaz tap debe estar asociada al bridge esperado.

    Paso 7. Observar ARP y tráfico¶

    tcpdump -eni vmbr1 arp or icmp

    Interpretación rápida:

    Observación Posible causa
    No sale ARP de la VM NIC apagada, IP/prefijo incorrectos, interfaz equivocada.
    Sale ARP, pero nadie responde Destino apagado, bridge equivocado, VLAN incorrecta, IP inexistente.
    Hay ARP y ping de ida, pero no respuesta Firewall o configuración del destino.
    Funciona IP remota, pero no nombres Problema DNS.
    Funciona red local, pero no gateway Gateway, red exterior o filtrado.

    Paso 8. Comparar con una máquina que funcione¶

    Comparar:

    ip -br addr
ip route
ip neigh

    Paso 9. Revisar firewall¶

    Dentro de la VM y en Proxmox, según el laboratorio.

    Paso 10. Documentar la causa¶

    Una incidencia debe cerrarse indicando:

    • síntoma;
    • causa;
    • prueba que confirmó la causa;
    • cambio aplicado;
    • prueba final;
    • medida preventiva.

    16. Soluciones orientativas para el profesorado¶

    16.1. Ideas clave del cuestionario¶

    1. El bridge conmuta tramas Ethernet entre interfaces.
    2. ens18 es un puerto físico o virtual del host; vmbr0 es el switch software.
    3. Porque la interfaz física forma parte del bridge y la identidad IP corresponde al dispositivo lógico de capa 3.
    4. Es la interfaz del host que conecta una NIC de una VM KVM con un bridge.
    5. Interfaces veth.
    6. VirtIO, cuando el sistema invitado dispone del controlador.
    7. Sí, si todos los equipos se encuentran en la misma subred y solo necesitan comunicación local.
    8. ip route.
    9. tcpdump -eni vmbrX arp or icmp.
    10. Desaparece o deja de estar activa porque está vinculada al proceso de la VM.
    11. /etc/network/interfaces.
    12. Porque un error puede interrumpir la interfaz web y SSH.
    13. La conmutación opera principalmente en capa 2; el encaminamiento comunica redes IP distintas.
    14. Asociaciones entre direcciones MAC y puertos del bridge.
    15. En ese orden, avanzando de las capas inferiores a las superiores.

    16.2. Explicación esperada: IP en el bridge¶

    Cuando una interfaz física se añade a un bridge, actúa como un puerto del switch virtual. La dirección IP de administración se asigna al bridge, que representa la interfaz lógica del host en esa red. Configurar simultáneamente la misma IP en el puerto y en el bridge genera una configuración incorrecta o ambigua.

    16.3. Diagnóstico del caso de bridges diferentes¶

    Dos VMs conectadas a vmbr1 y vmbr2 se encuentran en dominios de capa 2 separados. Aunque utilicen direcciones de la misma subred, no existe un camino de conmutación entre ellas. Se necesitaría conectarlas al mismo bridge o introducir un diseño de interconexión adecuado.

    19. Glosario¶

    Término Definición
    Bridge Switch Ethernet implementado por software.
    vmbrX Nombre habitual de un Linux bridge en Proxmox.
    NIC Interfaz o tarjeta de red.
    tap Interfaz del host asociada a una NIC de una VM KVM.
    veth Par de interfaces virtuales utilizado habitualmente por contenedores.
    FDB Tabla que relaciona MAC con puertos de un bridge.
    MAC Identificador de capa 2 de una interfaz Ethernet.
    Gateway Router utilizado para alcanzar otras redes.
    CIDR Notación de prefijo, por ejemplo /24.
    Broadcast Trama enviada a todos los equipos del dominio de capa 2.
    ARP Protocolo que relaciona direcciones IPv4 con direcciones MAC.
    ICMP Protocolo utilizado, entre otros fines, por ping.
    VirtIO Dispositivo paravirtualizado optimizado para máquinas virtuales.
    Uplink Enlace que conecta un bridge o switch con otra red.
    Red aislada Red sin conexión directa a una interfaz física o a un router exterior.
    Virtualización anidada Ejecución de un hipervisor dentro de una máquina virtual.
