    Laboratorios · UD1¶

    Los laboratorios de esta unidad siguen el ciclo:

    Predecir → configurar → comprobar → explicar

    El objetivo no es únicamente conseguir conectividad. Antes de modificar una configuración, el alumnado debe intentar responder:

    1. ¿Qué comunicación quiero conseguir?
    2. ¿Qué camino debería seguir el paquete?
    3. ¿Qué elementos de red intervienen?
    4. ¿Qué resultado espero obtener?
    5. ¿Cómo puedo demostrar que funciona?

    0. Preparación del entorno Proxmox¶

    Antes de comenzar los laboratorios debemos comprender cómo estará conectado el servidor Proxmox a la red física del aula.

    0.1 Arquitectura inicial¶

    El servidor dispone de una interfaz Ethernet física, que representaremos como:

    eno1

    El nombre real puede ser diferente:

    eno1
eno2
enp3s0
enp5s0
...

    Compruébalo mediante:

    ip -br link

    La red física del aula proporciona direccionamiento mediante DHCP.

    La arquitectura inicial será:

                     RED FÍSICA DEL AULA
                    DHCP + Internet
                          │
                          │
                         eno1
                          │
                          ▼
                        vmbr0
                       DHCP
                          │
                    Host Proxmox


                        vmbr1
                       sin IP
                          │
                   ┌──────┴──────┐
                   │             │
                  VM-A           VM-B

    Utilizaremos dos bridges con funciones diferentes:

    Bridge Función
    vmbr0 conexión del nodo Proxmox con la red física
    vmbr1 red privada de laboratorio

    0.2 Bridge de la red física: vmbr0¶

    La interfaz física no tendrá directamente la configuración IP:

    iface eno1 inet manual

    En su lugar, actuará como puerto de:

    vmbr0

    y será vmbr0 quien solicite una dirección mediante DHCP.

    eno1
  │
  │ puerto L2
  ▼
vmbr0
  │
  └── DHCP → dirección IP del nodo Proxmox

    Concepto importante

    Cuando una interfaz física se integra en un Linux Bridge, la configuración IP del host se realiza normalmente sobre el bridge, no sobre el puerto físico.

    0.3 Plantilla inicial de /etc/network/interfaces¶

    Una configuración simplificada de referencia será:

    auto lo
iface lo inet loopback

iface eno1 inet manual

auto vmbr0
iface vmbr0 inet dhcp
    bridge-ports eno1
    bridge-stp off
    bridge-fd 0

auto vmbr1
iface vmbr1 inet manual
    bridge-ports none
    bridge-stp off
    bridge-fd 0

    Adapta la interfaz física

    eno1 es únicamente un ejemplo.

    Antes de modificar la configuración debes identificar el nombre real de la interfaz física:

    ip -br link

    Acceso al nodo

    Un error en la configuración de vmbr0 puede dejar el servidor Proxmox sin conectividad.

    Antes de modificar la red de un nodo remoto asegúrate de disponer de acceso por consola física o por algún mecanismo alternativo de administración.

    0.4 ¿Qué hace esta configuración?¶

    Interfaz física¶

    iface eno1 inet manual

    No configura direccionamiento IP sobre eno1.

    Bridge físico¶

    auto vmbr0
iface vmbr0 inet dhcp
    bridge-ports eno1

    eno1 pasa a ser un puerto del bridge y:

    vmbr0 → DHCP

    obtiene la configuración de red del aula.

    Bridge interno¶

    auto vmbr1
iface vmbr1 inet manual
    bridge-ports none

    vmbr1:

    • no tiene dirección IP;
    • no está conectado a una NIC física;
    • no tiene gateway;
    • no proporciona acceso a Internet.

    Es simplemente un segmento Ethernet virtual interno.

    0.5 Validar la configuración inicial¶

    Después de aplicar la configuración:

    ip -br link

    Comprueba que existen:

    eno1
vmbr0
vmbr1

    Después:

    ip -br addr

    Debes observar que vmbr0 ha recibido una dirección de la red del aula.

    Puedes comprobar únicamente esa interfaz:

    ip -br addr show vmbr0

    Comprueba también la tabla de routing:

    ip route

    Debería existir una ruta por defecto aprendida mediante DHCP.

    Finalmente:

    ip route get 8.8.8.8

    te permitirá comprobar qué interfaz y siguiente salto utilizaría el nodo Proxmox para alcanzar Internet.

    0.6 Evolución de la red durante la unidad¶

    No configuraremos toda la infraestructura desde el principio.

    La iremos construyendo según aparezcan nuevas necesidades.

    Fase 1 · Switching¶

    VM-A ─────┐
          ├──── vmbr1
VM-B ─────┘

    Trabajaremos:

    Ethernet
MAC
ARP
Linux Bridge
FDB

    No habrá:

    gateway
routing
NAT
Internet

    Fase 2 · Routing¶

    Posteriormente el host Proxmox participará en la red interna:

    VM-A ─────┐
          │
VM-B ─────┼──── vmbr1 10.10.10.1
          │
          ▼
       Proxmox
          │
        vmbr0

    Esto permitirá introducir el concepto de gateway y routing.

    Fase 3 · NAT¶

    Finalmente podremos permitir que las máquinas privadas utilicen la conectividad exterior del nodo:

    10.10.10.0/24
       │
       ▼
vmbr1 10.10.10.1
       │
       ▼
 IPv4 forwarding
       │
       ▼
   MASQUERADE
       │
       ▼
vmbr0 → DHCP
       │
       ▼
Red aula → Internet

    Esta evolución es deliberada:

    switching
   ↓
routing
   ↓
NAT

    Laboratorio 1 · Direccionamiento IPv4 y CIDR¶

    Objetivo¶

    Interpretar correctamente una dirección IPv4 y su prefijo.

    Analiza:

    10.20.30.15/24

    Determina:

    • dirección del host;
    • red;
    • máscara;
    • número total de direcciones;
    • rango de hosts;
    • broadcast.

    Después analiza:

    10.20.34.15/20

    Pistas¶

    Pista 1

    No supongas que todas las redes terminan en /24.

    Pista 2

    Para /20:

    11111111.11111111.11110000.00000000
    Pista 3

    El tercer octeto de la máscara vale 240.

    Por tanto:

    256 - 240 = 16

    Las redes avanzan en bloques de 16 en el tercer octeto.

    Laboratorio 2 · Red aislada en Proxmox¶

    Objetivo¶

    Crear una red virtual Ethernet completamente aislada.

    VM-A
192.168.50.10/24
       │
       ▼
     vmbr1
       ▲
       │
VM-B
192.168.50.20/24

    Características:

    Router:   NO
Gateway:  NO
NAT:      NO
Internet: NO
VLAN:     NO

    Paso previo¶

    Comprueba que:

    ip -br link

    muestra vmbr1.

    También puedes utilizar:

    ip -d link show vmbr1

    Conectar las máquinas¶

    En Proxmox:

    VM
→ Hardware
→ Network Device
→ Bridge: vmbr1

    Hazlo en ambas VM.

    Configura:

    VM-A¶

    192.168.50.10/24

    VM-B¶

    192.168.50.20/24

    No configures gateway.

    Antes de hacer ping¶

    Predice el resultado:

    Origen Destino ¿Funcionará? ¿Por qué?
    VM-A VM-B
    VM-B VM-A
    VM-A Internet

    Solo después realiza las pruebas.

    Validación¶

    Dentro de las VM:

    ip -br link
ip -br addr
ip route

    Desde VM-A:

    ping -c 4 192.168.50.20

    Después:

    ip neigh

    Observar el bridge¶

    En Proxmox:

    bridge link

    y:

    bridge fdb show br vmbr1

    Debes poder relacionar:

    MAC de VM-A → puerto TAP
MAC de VM-B → puerto TAP

    Observar ARP e ICMP¶

    Dentro de una VM:

    sudo tcpdump -ni ens18 arp or icmp

    En Proxmox:

    tcpdump -ni vmbr1 arp or icmp

    Mientras se ejecuta la captura, realiza:

    ping -c 4 192.168.50.20

    Pistas¶

    Pista 1 · No aparece vmbr1

    Comprueba:

    ip -br link

    y revisa /etc/network/interfaces.

    Pista 2 · Las VM no comunican

    Comprueba que ambas utilizan:

    Bridge: vmbr1
    Pista 3 · Revisa el direccionamiento

    Debes tener:

    192.168.50.10/24
192.168.50.20/24

    Ambas pertenecen a:

    192.168.50.0/24
    Pista 4 · No añadas un gateway

    Un gateway no es necesario para comunicarse con otro host de la misma red.

    Laboratorio 3 · Romper la conectividad¶

    Cambia únicamente la dirección de VM-B:

    VM-A → 192.168.50.10/24
VM-B → 192.168.60.20/24

    Mantén ambas conectadas a:

    vmbr1

    Antes de modificar nada¶

    Responde:

    1. ¿Sigue funcionando vmbr1?
    2. ¿Siguen las VM en el mismo dominio Ethernet?
    3. ¿Pertenecen a la misma red IP?
    4. ¿Qué elemento sería necesario para comunicar ambas redes?

    Comprueba:

    ip route

    y:

    ip route get 192.168.60.20

    cuando proceda.

    Pistas¶

    Pista 1

    No ha cambiado la capa 2.

    Pista 2

    Calcula las redes de:

    192.168.50.10/24
192.168.60.20/24
    Pista 3

    Si existen dos redes IP diferentes, necesitarás un elemento que trabaje en capa 3.

    Laboratorio 4 · Introducción al routing en Proxmox¶

    Objetivo¶

    Evolucionaremos el bridge interno para que el nodo Proxmox participe en la red.

    Utilizaremos:

    10.10.10.0/24

    Arquitectura:

    VM-A 10.10.10.10
       │
       │
VM-B 10.10.10.20
       │
       ▼
vmbr1 10.10.10.1
       │
       ▼
    Proxmox

    Modificación de vmbr1¶

    La configuración pasa de:

    auto vmbr1
iface vmbr1 inet manual
    bridge-ports none
    bridge-stp off
    bridge-fd 0

    a:

    auto vmbr1
iface vmbr1 inet static
    address 10.10.10.1/24
    bridge-ports none
    bridge-stp off
    bridge-fd 0

    Ahora el host Proxmox tiene presencia IP en la red interna.

    Configuración de las VM¶

    VM-A¶

    IP:      10.10.10.10/24
Gateway: 10.10.10.1

    VM-B¶

    IP:      10.10.10.20/24
Gateway: 10.10.10.1

    Validación¶

    En Proxmox:

    ip -br addr show vmbr1

    Debe aparecer:

    10.10.10.1/24

    En VM-A:

    ip route

    Deberías observar conceptualmente:

    10.10.10.0/24 dev ens18
default via 10.10.10.1

    Comprueba:

    ping -c 4 10.10.10.1
ping -c 4 10.10.10.20

    Pregunta¶

    ¿Significa disponer ahora de gateway que VM-A ya puede acceder a Internet?

    Justifica la respuesta antes de probarlo.

    Laboratorio 5 · Salida a Internet mediante NAT¶

    Objetivo¶

    Permitir que las VM de:

    10.10.10.0/24

    salgan hacia Internet utilizando la conectividad de vmbr0.

    Arquitectura:

    VM-A 10.10.10.10
        │
VM-B 10.10.10.20
        │
        ▼
vmbr1 10.10.10.1
        │
        ▼
   IP forwarding
        │
        ▼
    MASQUERADE
        │
        ▼
vmbr0 → DHCP
        │
        ▼
    RED DEL AULA
        │
        ▼
      INTERNET

    5.1 Routing IPv4¶

    Linux debe poder reenviar paquetes entre interfaces.

    Comprueba:

    sysctl net.ipv4.ip_forward

    Para habilitarlo:

    sysctl -w net.ipv4.ip_forward=1

    5.2 NAT¶

    Como vmbr0 obtiene su dirección mediante DHCP, utilizaremos MASQUERADE.

    Conceptualmente:

    Origen:
10.10.10.10

        ↓ NAT

Origen hacia la red exterior:
IPv4 actual de vmbr0

    Ejemplo:

    iptables -t nat -A POSTROUTING \
  -s 10.10.10.0/24 \
  -o vmbr0 \
  -j MASQUERADE

    5.3 Plantilla de referencia¶

    La configuración puede evolucionar hacia:

    auto lo
iface lo inet loopback

iface eno1 inet manual

auto vmbr0
iface vmbr0 inet dhcp
    bridge-ports eno1
    bridge-stp off
    bridge-fd 0

auto vmbr1
iface vmbr1 inet static
    address 10.10.10.1/24
    bridge-ports none
    bridge-stp off
    bridge-fd 0

    post-up   sysctl -w net.ipv4.ip_forward=1
    post-up   iptables -t nat -A POSTROUTING -s '10.10.10.0/24' -o vmbr0 -j MASQUERADE
    post-down iptables -t nat -D POSTROUTING -s '10.10.10.0/24' -o vmbr0 -j MASQUERADE

    ¿Por qué MASQUERADE?

    La dirección de vmbr0 procede de DHCP y puede cambiar.

    MASQUERADE permite utilizar dinámicamente la dirección de la interfaz de salida sin escribir una IP concreta en la regla de SNAT.

    5.4 Predicción¶

    Completa antes de probar:

    Origen Destino Esperado Motivo
    VM-A VM-B
    VM-A 10.10.10.1
    VM-A Internet
    Internet VM-A

    5.5 Validación¶

    En VM-A:

    ip route

    Después:

    ping -c 4 10.10.10.1

    y finalmente prueba conectividad exterior.

    En Proxmox:

    ip route

    ip route get 8.8.8.8

    y comprueba las reglas NAT:

    iptables -t nat -L -n -v

    Pistas¶

    Pista 1 · La VM alcanza 10.10.10.1 pero no Internet

    Comprueba:

    sysctl net.ipv4.ip_forward
    Pista 2 · IP forwarding está activo

    Comprueba la tabla NAT:

    iptables -t nat -L -n -v
    Pista 3 · Revisa la salida de Proxmox

    Comprueba:

    ip route get 8.8.8.8

    y verifica que la salida corresponde a vmbr0.

    Pista 4 · No cambies varias cosas simultáneamente

    Determina primero si falla:

    VM → gateway
gateway → Internet
forwarding
NAT
DNS

    Laboratorio 6 · Construcción manual de una VPC en AWS¶

    Objetivo¶

    Reproducir en AWS los principios de red estudiados anteriormente.

    Crear:

    VPC:            10.0.0.0/16
Public Subnet:  10.0.1.0/24
Private Subnet: 10.0.2.0/24

    Utiliza:

    rc-ud1-vpc
rc-ud1-public-subnet
rc-ud1-private-subnet
rc-ud1-rt-public
rc-ud1-rt-private
rc-ud1-igw
rc-ud1-public-ec2
rc-ud1-private-ec2

    Construcción manual

    No utilices inicialmente asistentes que creen automáticamente toda la arquitectura.

    Queremos identificar cada dependencia.

    Orden recomendado¶

    VPC
 ↓
Subnets
 ↓
Route Tables
 ↓
Internet Gateway
 ↓
Rutas
 ↓
EC2

    Pistas¶

    Pista 1 · CIDR

    Comprueba:

    10.0.1.0/24 ⊂ 10.0.0.0/16
10.0.2.0/24 ⊂ 10.0.0.0/16
    Pista 2 · Availability Zone

    En esta unidad ambas subnets pueden estar en una misma AZ.

    Laboratorio 7 · Routing de la VPC¶

    Crea:

    rc-ud1-rt-public
rc-ud1-rt-private

    y realiza asociaciones explícitas:

    public-subnet  → rt-public
private-subnet → rt-private

    Observación¶

    Antes de añadir ninguna ruta, localiza:

    10.0.0.0/16 → local

    Pistas¶

    Pista 1

    local no significa localhost.

    Representa el routing interno del espacio de la VPC.

    Pista 2

    Que una Route Table exista no significa que una subnet la esté utilizando.

    Comprueba la asociación.

    Laboratorio 8 · Internet Gateway¶

    Crea:

    rc-ud1-igw

    y asócialo a:

    rc-ud1-vpc

    Solo en rt-public añade:

    0.0.0.0/0 → IGW

    La tabla privada permanecerá:

    10.0.0.0/16 → local

    Pistas¶

    Pista 1

    Crear el IGW no proporciona Internet automáticamente.

    Pista 2

    Comprueba:

    Subnet
   ↓
Route Table asociada
   ↓
0.0.0.0/0
   ↓
IGW

    Laboratorio 9 · Instancias EC2¶

    Crea una instancia en cada subnet.

    EC2 pública¶

    Subnet:      public-subnet
Private IPv4: sí
Public IPv4:  sí

    EC2 privada¶

    Subnet:       private-subnet
Private IPv4: sí
Public IPv4:  no

    Antes de lanzar cada instancia revisa:

    VPC
Subnet
IPv4 pública
Security Group

    Pista¶

    La IP pública no aparece con ip addr

    Es normal.

    Dentro de la instancia observarás principalmente la dirección privada de la ENI.

    No esperes encontrar necesariamente la IPv4 pública configurada directamente sobre la interfaz Linux.

    Laboratorio 10 · Recorrido del paquete en AWS¶

    Regla¶

    No hagas primero el ping.

    Primero determina qué ruta debería utilizarse.

    Caso A · EC2 pública → Internet¶

    Analiza:

    Destino público
      ↓
¿coincide con 10.0.0.0/16?
      ↓
NO
      ↓
0.0.0.0/0
      ↓
IGW

    Resultado esperado:

    EC2-PUBLIC
    ↓
rt-public
    ↓
0.0.0.0/0
    ↓
IGW
    ↓
Internet

    Caso B · EC2 pública → EC2 privada¶

    La dirección privada destino pertenece a:

    10.0.0.0/16

    Por longest-prefix match se utilizará:

    10.0.0.0/16 → local

    No interviene el IGW.

    Caso C · EC2 privada → Internet¶

    Observa exclusivamente rt-private.

    Si solo contiene:

    10.0.0.0/16 → local

    no existe una ruta hacia Internet.

    El fallo es el resultado esperado.

    No añadas NAT Gateway

    Precisamente la necesidad de proporcionar salida a Internet a una subnet privada sin convertirla en pública será uno de los problemas que resolveremos posteriormente.

    Matriz final de conectividad¶

    Completa la matriz:

    Origen Destino Ruta Esperado Resultado
    Proxmox VM-A Proxmox VM-B red local ✅
    VM-A NAT Internet Proxmox + NAT ✅
    public-ec2 private-ec2 10.0.0.0/16 → local ✅*
    private-ec2 public-ec2 10.0.0.0/16 → local ✅*
    public-ec2 Internet 0.0.0.0/0 → IGW ✅*
    private-ec2 Internet ninguna ❌

    * Siempre que las políticas de seguridad permitan el tráfico.

    Ayudas generales de troubleshooting¶

    Proxmox / Linux¶

    Sigue este orden:

    1. Interfaz
       ↓
2. Dirección y prefijo
       ↓
3. Red local
       ↓
4. Gateway
       ↓
5. Tabla de routing
       ↓
6. IP forwarding
       ↓
7. NAT
       ↓
8. DNS / aplicación

    Comandos:

    ip -br link
ip -br addr

    Para NAT:

    sysctl net.ipv4.ip_forward

    Qué NO hacer¶

    Evita estas estrategias

    • reiniciar sin conocer la causa;
    • cambiar varias configuraciones simultáneamente;
    • abrir todos los puertos;
    • añadir rutas por probar;
    • configurar gateways innecesarios;
    • añadir NAT para resolver cualquier problema;
    • copiar configuraciones sin comprenderlas.

    Antes de pedir ayuda¶

    Debes poder indicar:

    1. Qué comunicación intentas realizar.
2. Cuál es el origen.
3. Cuál es el destino.
4. Qué resultado esperabas.
5. Qué resultado has obtenido.
6. Qué camino debería seguir el paquete.
7. Qué comprobaciones has realizado.
8. Cuál es tu hipótesis.

    Una consulta técnica adecuada sería:

    La VM alcanza 10.10.10.1, pero no alcanza Internet. La ruta por defecto apunta a 10.10.10.1. He comprobado que Proxmox sí tiene salida por vmbr0. Mi siguiente comprobación será verificar net.ipv4.ip_forward y la regla de MASQUERADE.

    Evidencias mínimas¶

    El alumnado deberá conservar:

    1. diagrama de la arquitectura;
    2. tabla de direccionamiento;
    3. configuración de bridges;
    4. configuración IP de las VM;
    5. tablas de routing;
    6. FDB y tabla de vecinos cuando corresponda;
    7. configuración VPC y subnets;
    8. asociaciones subnet–Route Table;
    9. rutas;
    10. Internet Gateway;
    11. direccionamiento de las EC2;
    12. matriz de conectividad;
    13. explicación razonada de, al menos, un caso que no funcione.
